1 重构动机与核心原则

明确 LLM 与传统系统的职责边界，消除面试中"LLM 设计过度"的质疑

核心原则：LLM 负责语义理解 / 创意生成 / 灰度仲裁，传统系统负责确定性计算 / 低延迟任务 / 可审计逻辑。

重构前：8 个 Agent 混用

  • 所有模块都继承 BaseAgent，无论是否使用 LLM
  • FraudDetectionAgent 内部虽有确定性规则引擎，但被包装为 Agent
  • CreditAssessmentAgent 使用评分卡，本质是确定性计算，却走 Agent 四层防护
  • SupplyChainAgent 的 Saga 事务编排被包在 Agent 框架内，增加了不必要的 LLM ReAct 复杂度
  • KGUserProfileAgent 的分群逻辑是规则引擎，却被命名为 Agent
  • 面试时难以解释"为什么确定性逻辑要叫 Agent"
  • LLM ReAct 链路降级为"探索性功能"后仍占据主链路代码位置

重构后：3 Agent + 7 Service

  • 只有真正调用 LLM 的模块才叫 Agent（ProductRecAgent, MarketingCopyAgent, MetaAgent）
  • 确定性逻辑全部迁移到 Service 层，继承 BaseProtectedService
  • Service 保留熔断 + 超时 + 降级三层防护（去掉重试层，业务操作多为非幂等）
  • Agent 保留完整四层防护（重试 + 超时 + 降级 + 熔断），因为 LLM 调用可能瞬时抖动
  • 职责边界清晰：面试时可明确回答"哪些用 LLM，哪些不用"
  • 编排层（graph.py / dynamic_engine.py）统一调用 Service.run() 和 Agent.run()

4 基类设计对比

BaseAgent (四层防护) vs BaseProtectedService (三层防护) 的差异

防护层 BaseAgent (LLM Agent) BaseProtectedService (传统 Service) 差异说明
L1 重试 ✓ 指数退避 2 次 ✓ 指数退避 1 次 Service 减少重试次数 — 业务操作多为非幂等（扣减库存、创建订单），重复执行可能导致重复扣减
L2 超时 ✓ asyncio.wait_for ✓ asyncio.wait_for 相同 — 独立超时控制防止长尾阻塞
L3 降级 ✓ _fallback() ✓ _fallback() 相同 — 失败时返回降级结果，保证链路不中断
L4 熔断 ✓ CircuitBreaker ✓ CircuitBreaker 相同 — 滑动窗口错误率监控，OPEN 时直接降级
抽象方法 _execute() execute() 命名差异：Agent 用 protected _execute，Service 用 public execute
LLM 依赖 ✓ get_llm() / ReAct ✗ 无 LLM Service 不调用 LLM，不使用 ReAct 工具选择，纯确定性逻辑 
# BaseAgent — LLM Agent 基类 (四层防护)

    async def run(self, **kwargs) -> AgentResult:
        # L4: 熔断检查 → L1: 重试(2次) + L2: 超时 → _execute()
        ...
    async def _execute(self, **kwargs) -> AgentResult:  # 子类实现 LLM 逻辑
        ...

# BaseProtectedService — 传统 Service 基类 (三层防护)
class BaseProtectedService(ABC):
    async def run(self, **kwargs) -> AgentResult:
        # L4: 熔断检查 → L1: 重试(1次) + L2: 超时 → execute()
        ...
    async def execute(self, **kwargs) -> AgentResult:   # 子类实现确定性逻辑
        ...

7 新建 Service 详细说明

每个 Service 的核心逻辑、降级策略、与旧 Agent 的差异

FraudService Service

反欺诈规则引擎 — 确定性检测，亚毫秒级响应

  • 主链路: risk_tools.check_fraud() — IP/设备黑名单 + 行为规则 + 历史欺诈
  • 降级策略: 返回 HIGH 风险 + needs_human_review=True（保守策略）
  • 与旧 Agent 差异: 去掉 LLM ReAct 链路和 MCP 工具选择，规则引擎成为唯一路径
  • 超时: 8s | 重试: 1 次

CreditService Service

信用评分引擎 — 确定性评分卡，可审计可解释

  • 主链路: risk_tools.assess_credit() — 信用档案查询 + 额度评估 + 利率计算
  • 降级策略: 返回 approved=False, credit_score=0（拒绝授信）
  • 与旧 Agent 差异: 去掉 LLM ReAct，评分卡 100% 可复现
  • 超时: 8s | 重试: 1 次

RefundRiskService Service

退款风控规则引擎 — 确定性检测，分级处理

  • 主链路: risk_tools.assess_refund_risk() — 频率/金额/历史/理由规则
  • 降级策略: 返回 MANUAL_REVIEW + HIGH 风险（人工介入）
  • 与旧 Agent 差异: 去掉 LLM ReAct，规则引擎直接判定
  • 超时: 8s | 重试: 1 次

FulfillmentService Service

供应链履约 Saga 编排 — 确定性事务 + 四层防护补偿

  • 主链路: run_fulfillment_saga() — 库存校验→预占→物流匹配→订单创建
  • 降级策略: 返回 success=False + 错误信息
  • 与旧 Agent 差异: Saga 编排从 Agent 内提取为独立 Service，每步有独立熔断器
  • 超时: 12s | 重试: 1 次

ProfileService Service

用户画像 — Neo4j 图谱特征 + 确定性规则分群

  • 主链路: KGStore.get_profile_features() + RFM 规则分群
  • 降级策略: 返回 NEW_USER 默认画像
  • 与旧 Agent 差异: 去掉 LLM 分群推断，10-20x 更快，100% 可复现
  • 超时: 可配置 | 重试: 2 次（读操作幂等）

InventoryService Service

库存查询与预警 — 确定性库存校验

  • 主链路: 遍历商品检查库存 + 安全库存预警 + 限购策略
  • 降级策略: 返回空可用列表（安全优先）
  • 与旧 Agent 差异: 从 Agent 迁移为 Service，逻辑不变
  • 超时: 可配置 | 重试: 1 次

8 保留的 3 个 LLM Agent

每个 Agent 为何保留 LLM — 明确的 LLM 价值点

ProductRecAgent LLM Agent

商品推荐 — LLM 语义重排

  • LLM 用途: 语义级商品排序（理解用户意图 vs 机械匹配）
  • 召回层: 协同过滤 + Milvus 向量检索 + 热度策略（确定性，无 LLM）
  • 重排层: LLM 结合用户画像 + 知识图谱上下文做语义重排
  • 为何不能改为 Service: "看了手机壳→可能在找配件而非新手机"需要语义推理
  • LLM 模型: DeepSeek-V3 (deepseek-chat)

MarketingCopyAgent LLM Agent

营销文案 — LLM 创意生成

  • LLM 用途: 个性化营销文案生成（创意表达）
  • 模板系统: 按用户分群（新客/老客/高价值/价格敏感/流失风险）选择 Prompt
  • 合规校验: 敏感词过滤 + 广告法检查（确定性规则）
  • 为何不能改为 Service: 文案创作本质是创意生成，无法用规则穷举
  • LLM 模型: DeepSeek-V3 (deepseek-chat)

MetaAgent LLM Agent

跨域仲裁 — LLM 灰度决策

  • LLM 用途: 灰度区间（30≤risk<100）的模糊决策 + 跨域信号冲突仲裁
  • 规则快通道: risk≥100 直接拒绝，risk<30 直接通过（确定性，<1ms）
  • 灰度通道: LLM 综合各 Service 结果权衡后决策
  • 降级: LLM 不可用时回退规则引擎
  • 为何不能改为 Service: 灰度区间需要综合判断，规则无法覆盖所有组合
  • LLM 模型: DeepSeek-R1 (deepseek-reasoner)

10 关键设计决策

重构中的核心权衡和选择

决策 1 — 为什么 Service 去掉重试层？
业务操作（扣减库存、创建订单、预占库存）多为非幂等操作，重试可能导致重复扣减。保留 max_retries=1 仅用于网络瞬时抖动，Agent 保留 max_retries=2 因为 LLM 调用更可能瞬时失败且幂等。
决策 2 — 为什么 MetaAgent 提升为独立 Agent？
原来是 dynamic_engine.py 的内部类，职责不清晰。提取为 agents/meta_agent.py 后：(1) 明确它是 3 个 LLM Agent 之一；(2) 规则快通道 + LLM 仲裁双路径更清晰；(3) 独立测试更方便。
决策 3 — 为什么 ProfileService 保留 max_retries=2？
用户画像是读操作（Neo4j 查询 + Redis 读取），幂等可安全重试。其他 Service 操作多为写操作（扣减、创建、预占），降为 1 次。
决策 4 — 为什么 IntentRouter 用规则优先 + LLM 兜底？
意图路由是高频低延迟操作，关键词规则匹配 <1ms 即可覆盖 90% 场景。LLM 兜底仅用于关键词无法匹配的边缘情况，可通过配置 intent_router_use_llm 开关控制。
