# 一、项目背景

### 1. 项目名称
Multi-Agent E-Commerce System(多智能体电商系统)v2.0 —— 代码入口 `main.py` 声明为"推荐+风控+履约+售后全链路 Agent 协同"。

### 2. 项目所属业务领域
电商 + 金融分期购(代码与文档中多处出现"分期购场景""分期授信""信用支付"),核心是**推荐个性化**与**交易风控决策**。

### 3. 项目产生的业务背景
【待补充】资料中仅有 `docs/简历-项目经历.md` 的表述:某**大型金融电商项目**中的"智能体编排子系统",以 **PoC 形态**交付,定位是"在保持传统后端强一致、可解释、稳定的前提下,引入 LLM 辅助推荐与跨域决策"。更具体的业务方、立项时间、团队背景均无资料,需用户补充。

### 4. 解决的核心业务问题
在电商交易链路中同时满足两个看似冲突的目标:
- **个性化/智能化**:推荐语义化重排、个性化营销文案、跨域风险综合仲裁;
- **确定性/可控性**:风控、授信、履约必须可复现、可解释、不因 LLM 故障而中断。

### 5. 原有方案/传统方案存在什么问题
【部分有代码依据,部分需补充】
- 代码注释明确提到"旧版 UserProfileAgent 用 LLM 做分群推断"的问题:**黑盒、不可复现、慢**(ProfileService 注释:"较旧版 LLM 分群 10-20x 更快、100% 可复现")。
- 【待补充】推荐链路此前如何做、风控人工审核流程原状、履约自动化程度等背景,资料中没有。

### 6. 为什么需要开发这个项目
核心论据(可讲给面试官):
1. 单一 LLM 链路无法同时满足"智能"与"确定可控",需要按问题域分层选型;
2. 风控/履约等环节要求可审计、可解释、可回滚,LLM 不能直接做主写操作;
3. 需要一个统一入口承接多个场景(推荐/风控/授信/退款/履约),避免每场景一套系统;
4. 工程上需要一套可复用的容错体系(重试/超时/降级/熔断)兜底 LLM 与外部依赖故障。

### 7. 项目的核心目标
交付一个"LLM 辅助传统后端业务、而非替换"的多智能体编排子系统样板:端到端跑通推荐→风控→授信→履约→售后链路,且具备安全网关、可观测性、容错机制,达到真实企业工程验收标准(PoC)。

### 8. 项目最终面向的用户或业务角色
- 直接使用方:电商 App/Web 的用户(获得个性化推荐、信用分期、退款服务);
- 业务角色:风控审核人员(接收 escalate/人工预订单)、运营(查看 A/B 实验)、后端调用方(调用 v1/v2 API)。
【待补充】具体业务方与用户规模。

### 9. 项目的核心业务价值
- 推荐侧:多路召回 + LLM 语义重排 + 个性化文案,提升推荐的语义相关性与可解释性;
- 风控侧:确定性规则 + 跨域仲裁 + 人工兜底(HITL),兼顾准确与安全;
- 履约侧:Saga 保证最终一致性,高价值商品自动加密保价;
- 架构侧:为"LLM + 确定性混合"范式提供了一套可复制的工程样板。

> **一句话回答"为什么要做这个项目"**:在电商交易这个强一致、高合规的领域,单靠 LLM 无法直接落地生产,项目用"LLM 智能体负责语义/创意/灰度决策 + 确定性链路负责计算/风控/写操作"的混合架构,把大模型能力安全地接进交易链路,同时通过四层防护与 Saga 保证不因 AI 故障而丢单、错单。

# 二、业务流程

## 2.1 角色-能力对照(先厘清各模块定位)

| 组件 | 类型 | 在链路中的职责 |
|---|---|---|
| `IntentRouter` | 规则分发器(LLM 兜底默认关闭) | 意图识别与路由 |
| `ProductRecAgent` | LLM Agent | 多路召回 + LLM 语义重排 |
| `MarketingCopyAgent` | LLM Agent | 个性化文案生成 + 合规校验 |
| `MetaAgent` | LLM Agent | 跨域风险仲裁(规则快通道 + LLM 灰度) |
| `ProfileService` | 确定性 Service | 用户画像(RFM 规则分群,非 LLM) |
| `FraudService` / `CreditService` / `RefundRiskService` | 确定性 Service | 反欺诈 / 授信 / 退款风控规则引擎 |
| `InventoryService` | 确定性 Service | 库存校验 / 预警 / 限购 |
| `FulfillmentService` | 确定性 Service | Saga 履约编排 |
| `fulfillment_tools.py` / `risk_tools.py` | 纯函数工具层 | 确定性业务原语(被 Service 与 MCP 共用) |
| `mcp_fulfillment_server.py` / `mcp_risk_server.py` | MCP Server | 将工具以 MCP 协议暴露给外部客户端 |
| PostgreSQL | 关系库 | 订单 / 仓库 / 库存 / 物流路线主数据 |
| Redis | 缓存 / 分布式协调 | 限流、预占锁与预占池、CF 双向索引、行为序列、订单缓存 |
| Milvus | 向量库 | 商品向量 ANN 召回 |
| Neo4j | 图数据库 | 用户-商品图谱、画像特征、多跳召回、GraphRAG 证据 |

**数据传递方式**:LangGraph `State` 贯穿全链路——各节点返回 partial state,由 LangGraph channel 合并(reducer 处理 `agent_results` 的并行合并);节点间通过共享 state 传递 `user_profile / raw_products / ranked_products / available_ids / final_products / marketing_copies / agent_results` 等。

## 2.2 正常业务流程

### 链路 A:个性化推荐(v1 `/api/v1/recommend` 或 v2 `intent=recommendation`)

```
① 请求进入 FastAPI → 安全网关中间件(限流 → JWT鉴权 → PII脱敏 → Prompt注入检测)
② init_node:分配 request_id、A/B 实验组(一致性哈希分桶,默认 rec_strategy)
③ 并行(user_profile ‖ product_recall)
   3a. ProfileService:从 Neo4j 拉取行为特征 → 上下文冷启动覆盖 → RFM 规则分群 → UserProfile
   3b. ProductRecAgent._recall:向量(Milvus)+ 协同过滤(Redis)+ 图谱(Neo4j)+ 热度 四路召回,去重合并
④ 并行(rerank ‖ inventory)【等待 ③ 全部完成】
   4a. ProductRecAgent._rerank:确定性打分(类目/价格/多样性)→ top-N 交给 LLM 语义重排 → 失败回退确定性排序
   4b. InventoryService:过滤无库存商品、生成低库存预警、计算限购数量
⑤ filter:ranked_products ∩ available_ids(交集为空则回退 ranked)
⑥ marketing_copy:GraphRAG 子图证据 + 用户分群模板 → LLM 生成文案 → 广告法敏感词过滤
⑦ aggregate:计算总耗时 → 返回 RecommendationResponse
```

### 链路 B:统一动态引擎(v2 `/api/v2/process`)

```
① 安全网关中间件(同上)
② intent_router_node:
   - 调用方显式传 intent → 直接采用(confidence=1.0)
   - 否则关键词规则匹配(INTENT_KEYWORDS,置信度 = min(0.9, 0.5 + 命中数*0.15))
   - LLM 意图识别默认关闭(settings.intent_router_use_llm=False)
③ 条件边 route_by_intent 分发到 5 条分支之一:
   - recommendation → recommendation_branch(内嵌调用完整推荐图)
   - fraud_check → fraud_branch(FraudService 规则引擎)
   - credit_assessment → credit_branch(CreditService 评分卡)
   - refund_review → refund_branch(RefundRiskService 规则引擎)
   - fulfillment → fulfillment_precheck(见链路 C)
④ meta_agent_node:汇总各分支结果,规则快通道 / LLM 仲裁(见第六章)
⑤ 组装 UnifiedResponse 返回
```

### 链路 C:履约(写操作,带门控)

```
① fulfillment_precheck:
   - 先并行跑 FraudService + CreditService
   - MetaAgent.decide(FULFILLMENT, results)
   - 决策:approve → 允许真实下单;reject/escalate → 只生成"待人工预订单"(不落单、不占库存)
② 条件边 route_fulfillment:
   - approve → fulfillment_execute → FulfillmentService → Saga 4 步:
     check_inventory → reserve_inventory(Redis SETNX 锁+预占池,15min TTL)
     → match_logistics_route(高价值≥3000 强制加密保价)→ create_order(落 PostgreSQL)
   - reject/escalate → fulfillment_pending → 返回 pending_order(needs_human_review=True)
```

### 链路 D:反向接口(运维/可观测)
`/api/v2/traces`(链路追踪)、`/api/v1/metrics`(Agent/业务指标)、`/api/v1/experiments`(A/B 状态)、`/api/v2/workflows`(工作流)、`/api/v1/llm/status`(多模型路由状态)。

## 2.3 异常业务流程

| 异常 | 处理机制 | 代码位置 |
|---|---|---|
| LLM 调用失败/超时 | BaseAgent 四层防护:指数退避重试(≤2 次)→ 独立超时 → 降级结果(如文案空列表、重排回退确定性排序) | `base_agent.py` |
| LLM 重排输出非 JSON / ID 非法 | `_llm_rerank` 解析失败返回 `[]`,`_rerank` 回退 `_score_candidates` 确定性排序 | `product_rec_agent.py` |
| 外部依赖不可用(Redis/Milvus/Neo4j/PostgreSQL) | 全部有降级路径:Redis→进程内存、Milvus→内存余弦、Neo4j→mock 数据、DB→硬编码默认值 | 各 store 文件 |
| 熔断触发(错误率≥50% 滑动窗口) | 直接走降级,不再调用故障组件;恢复期 30s 后 HALF_OPEN 探测 | `circuit_breaker.py` |
| Saga 某步失败 | 逆序补偿已执行步骤(release_inventory / cancel_order);补偿也带独立熔断;补偿失败记 COMPENSATE_FAILED 不阻断后续 | `saga.py` |
| 库存预占失败 | 返回 insufficient/locked 状态,Saga 判定业务失败不触发熔断(仅异常触发),触发补偿 | `fulfillment_tools.py` |
| 履约被 Meta 拒绝/升级 | 不落真实订单、不占库存,仅生成待人工预订单(HITL) | `dynamic_engine.py` |
| 请求超限/未认证/注入/敏感信息 | 安全网关返回 429/401/403;PII 入站脱敏 + 出站脱敏 | `guardrails.py` |
| 订单落库失败 | `create_order` 返回 `persist_failed`,并记录错误日志(注意:此时订单在缓存/内存已生成,存在不一致风险,见第十四章) | `fulfillment_tools.py` |
| 意图无法识别 | 路由到 recommendation_branch 兜底(而非报错) | `dynamic_engine.py` |

> **注意**:欺诈规则中 `order_count_1h` / `city_mismatch` 使用 `random` 模拟实时特征(**结果不可复现**,`risk_tools.py` L173-174),面试需知悉这是演示代码。

# 四、技术栈

| 分类 | 技术 | 使用场景 | 为什么使用 |
|---|---|---|---|
| 编程语言 | Python 3.12(Dockerfile 镜像) | 全部后端代码 | AI 生态成熟、FastAPI/LangChain 原生支持 |
| Web 框架 | FastAPI + Uvicorn | REST API 入口 | 异步、Pydantic 校验、中间件生态 |
| Agent 框架 | LangGraph(StateGraph) | 推荐图 + 动态引擎编排 | 原生 fan-out/fan-in、条件边、State 合并 |
| LLM 集成 | LangChain(ChatOpenAI)、langchain-openai | 统一调用 DeepSeek / vLLM | OpenAI 兼容协议统一适配 |
| LLM | DeepSeek-V3(deepseek-chat)/ DeepSeek-R1(deepseek-reasoner);vLLM 本地 Qwen2.5-7B | 重排/文案/仲裁/意图兜底 | 成本与推理能力分级 |
| Embedding | sentence-transformers + BAAI/bge-small-zh-v1.5 | 商品语义向量 | 中文语义检索,512 维轻量 |
| RAG | GraphRAG(自研,基于 Neo4j 子图) | 为 LLM 重排/文案注入图谱证据 | 商品关联/多跳路径增强可解释性 |
| 向量数据库 | Milvus(pymilvus, HNSW+COSINE) | 商品向量 ANN 召回 | 生产级 ANN;内存余弦降级 |
| 关系数据库 | PostgreSQL + SQLAlchemy + psycopg2 | 订单、仓库、库存、物流主数据 | 强一致、事务 |
| 缓存/协调 | Redis(redis-py asyncio) | 限流滑动窗口、预占分布式锁、CF 索引、行为特征、订单缓存 | 原子操作、TTL |

# 五、Agent 职责

> 项目严格区分 **3 个 LLM Agent** 与 **6 个确定性 Service**(文档/代码注释明确"传统业务 Service,非 LLM Agent")。本节逐个分析 LLM Agent;Service 简列。

## 5.1 ProductRecAgent(商品推荐 Agent,LLM)

| 项 | 内容 |
|---|---|
| 核心职责 | 多路召回 + LLM 语义重排 |
| 输入 | user_id、user_profile(可选)、num_items |
| 输出 | ProductRecResult(products、recall_strategy、data) |
| 使用的 LLM | `task_type=recommendation_rerank` → general(DeepSeek-V3),temperature=0.3 |
| 使用的 Tools | 不直接调工具;内部使用 MilvusStore / CFStore / KGStore / GraphRAGService |
| MCP Server | 无 |
| 是否访问数据库 | 间接:Milvus(向量)、Redis(CF)、Neo4j(图谱) |
| 是否调用其他 Agent | 否(被编排图调度) |
| 在 Workflow 中的位置 | 推荐图 Stage1(召回)+ Stage2(重排) |
| 为什么需要 | 召回要覆盖多源(向量/协同/图谱/热度),重排需要语义理解用户意图 |

关键实现细节:
- 召回顺序:vector + CF + graph + popularity → 去重合并 → 打分排序(类目偏好 +0.3、价格区间 +0.2、类目多样性 +0.1)→ 截取 limit;
- 重排:确定性 `_score_candidates` 排序 → 仅 top `num_items*2` 交 LLM → LLM 失败回退确定性排序;
- 知识图谱上下文:GraphRAG 将"商品关系/多跳候选/相似用户/热点商品"拼为文本注入 prompt。

## 5.2 MarketingCopyAgent(营销文案 Agent,LLM)

| 项 | 内容 |
|---|---|
| 核心职责 | 按用户分群生成个性化文案 + 广告法合规校验 |
| 输入 | user_profile、products、graph_context(可选) |
| 输出 | MarketingCopyResult(copies: [{product_id, copy}], prompt_template_used) |
| 使用的 LLM | `task_type=marketing_copy` → general(V3),temperature=0.9(创意) |
| 使用的 Tools | 无;内部 `_compliance_check` 规则过滤 FORBIDDEN_WORDS(最好/第一/国家级/100% 等) |
| 是否访问数据库 | 否 |
| 是否调用其他 Agent | 否 |
| 为什么需要 | 文案生成是典型创意任务;分群模板(新客/高价值/价格敏感/流失召回)提升针对性 |

## 5.3 MetaAgent(跨域仲裁 Agent,LLM)

| 项 | 内容 |
|---|---|
| 核心职责 | 综合多 Service 结果做最终决策(approve / escalate / reject) |
| 输入 | intent、agent_results(fraud/refund/credit/supply 等结果) |
| 输出 | MetaDecisionResult(final_decision、reason、aggregated_risks、escalation_required、arbitration_source) |
| 使用的 LLM | `task_type=meta_decision` → reasoning(DeepSeek-R1),temperature=0.1 |
| 使用的 Tools | 无 |
| 是否访问数据库 | 否(只消费其他 Service 输出) |
| 是否调用其他 Agent | 否 |
| 在 Workflow 中的位置 | 动态引擎收尾节点;履约预检中也单独调用 |
| 为什么需要 | 跨域冲突(如欺诈高但信用好)需要综合仲裁,不能靠单一规则或单一 LLM |

**双路径决策逻辑(面试重点,务必记牢)**:
1. **履约+授信特殊规则**:credit.approved 且 approved_amount>0 → approve;否则 escalate;
2. **规则快通道**:总风险分 ≥100 → reject;`<30` → approve;
3. **LLM 仲裁触发条件**(任一):
   - 推荐场景:fraud.risk_score>40 且推荐商品最高价>5000 且 fraud.risk_score>50;
   - 退款场景:refund≥30 且 fraud≥30;
   - 跨域冲突:max(risks)≥60 且 min(risks)≤20;
   - 灰度区间:30 ≤ total_risk < 100;
4. **降级**:LLM 仲裁异常 → `_rule_fallback`(total_risk≥60 → escalate,否则 approve)。

风险分构成:fraud.risk_score、refund.risk_score、credit = max(0, (900-credit_score)/6)。

## 5.4 确定性 Service(非 LLM,简列)

| Service | 核心逻辑 | 数据源 |
|---|---|---|
| ProfileService | Neo4j 特征 + RFM 规则分群(替代旧 LLM 画像) | Neo4j / 上下文 |
| FraudService | 7 条反欺诈规则加权评分 | risk_tools(内存) |
| CreditService | 评分卡:信用分→额度→利率(日息万3/5/8) | risk_tools(内存) |
| RefundRiskService | 5 条退款规则→极速退款/待审核/人工 | risk_tools(内存) |
| InventoryService | 库存过滤/预警(≤50 critical, ≤100 warning)/限购 | 商品自带 stock 字段 |
| FulfillmentService | Saga 4 步编排 + 补偿 | PostgreSQL/Redis |

## 5.5 为什么不能用一个 Agent 解决全部问题(面试问答模板)

1. **能力差异**:语义重排(创造)、文案(创意)、仲裁(推理)对模型能力/温度/成本要求不同,统一 Agent 要么浪费要么不足——用多模型路由+分 Agent 隔离;
2. **确定性要求**:风控/授信/履约是写操作与合规环节,必须可复现、可审计、可回滚,不能交给 LLM(幻觉/不可复现)→ 拆为确定性 Service;
3. **故障隔离**:LLM 挂了,风控/履约仍要能运行(降级);单一 Agent 会全链路崩溃;
4. **可解释性**:每个环节独立成 Agent/Service,产出独立 result + confidence,便于追踪/审计/定位;
5. **扩展性**:新增场景(如优惠券风控)只加一个 branch,不改主链路。

**为什么按"3 LLM Agent + 6 Service"拆分**:按"问题域"拆分(推荐域/文案域/仲裁域 + 风控域/授信域/退款域/库存域/履约域),每个域单一职责;LLM 只出现在"需要语义/创意/灰度判断"的地方,确定性计算留在 Service。

# 六、LangGraph / Workflow 流程

## 6.1 推荐图(graph.py)—— 三阶段并行拓扑

1. **State**:`PipelineState`(TypedDict)
   - 核心字段:user_id / scene / num_items / user_profile / raw_products / ranked_products / available_ids / final_products / marketing_copies / experiment_group / agent_results / total_latency_ms
   - `agent_results` 使用自定义 reducer `_merge_agent_results`(并行分支合并子字典);其余字段单节点写入无冲突;
2. **Node**(8 个):init → user_profile / product_recall → rerank / inventory → filter → marketing_copy → aggregate;
3. **Edge**:init fan-out 到 Stage1;Stage1 两节点同时指向 rerank/inventory(**fan-in 即 join**);Stage2 同时指向 filter(join);filter → marketing_copy → aggregate → END;
4. **条件路由**:本项目推荐图无条件边(全部确定性 DAG);条件路由在动态引擎;
5. **循环**:无循环(纯 DAG);
6. **失败处理**:节点内 Agent 自带四层防护,失败返回降级结果,不中断图;LLM 重排失败回退确定性排序;
7. **重试**:BaseAgent 层 tenacity 指数退避,不依赖 LangGraph;
8. **执行顺序控制**:通过边拓扑 + fan-in 语义保证(全部前置节点完成才执行);
9. **防无限循环**:无循环结构,天然安全;
10. **结果汇总**:aggregate 计算总耗时,最终 products/文案由 filter/marketing_copy 写入。

**流程表示**:
```
用户请求 → init(AB分桶) → [user_profile ‖ product_recall](并行)
  → join → [rerank ‖ inventory](并行) → join → filter(交集)
  → marketing_copy → aggregate → 最终结果
```

## 6.2 动态引擎(dynamic_engine.py)—— 意图路由 + 条件分支 + Meta

1. **State**:`DynamicState(dict)`(灵活 dict,承载各场景数据);
2. **Node**(9 个):init(intent_router)→ 5 分支 + fulfillment_precheck/execute/pending → meta_agent;
3. **Edge**:
   - `init` → 条件边 `route_by_intent` → 5 分支;
   - 4 个普通分支 → meta_agent → END;
   - fulfillment_precheck → 条件边 `route_fulfillment`(approve→execute / 其他→pending)→ END;
4. **条件路由实现**:`graph.add_conditional_edges("init", route_by_intent, {...})` 与 `add_conditional_edges("fulfillment_precheck", route_fulfillment, {...})`;
5. **Agent 协作**:分支节点调用各 Service/Agent,结果写入 state,meta_agent 汇总决策;
6. **失败处理**:同推荐图(四层防护 + 降级);履约分支失败不会落单;
7. **最终结果汇总**:meta_agent_node 计算 total_latency_ms 并写 meta_decision。

**流程表示**:
```
用户请求 → init(意图识别)
  → 条件边:recommendation | fraud | credit | refund | fulfillment
  → 对应分支(推荐图 / 规则引擎 / 评分卡 / 规则引擎 / 预检+门控)
  → meta_agent(规则快通道 | LLM 仲裁 | 规则降级)
  → END(履约分支:approve→真实Saga下单;否则→待人工预订单)
```

> **注意**:v2 的 `recommendation_branch` 每次调用都会 `build_recommendation_graph()` **重新构建并编译图**(L228-229),存在不必要的性能开销与对象重建,是可优化点(面试可主动提出)。

# 七、MCP 与工具调用体系

## 7.1 事实清单(严格区分"决策"与"执行")

| 问题 | 事实 |
|---|---|
| 为什么需要 MCP | 将履约/风控能力以标准协议暴露,供外部 MCP 客户端、运维工具、第三方集成复用 |
| MCP 解决了什么 | 工具标准化(stdio/streamable-http 双传输)、工具发现/描述、参数 schema 由工具定义 |
| MCP Client 是什么 | 仓库内**没有实现 MCP Client 调用主链路的代码**;`langchain-mcp-adapters` 已引入 requirements 但主链路未使用 |
| MCP Server 是什么 | `mcp_fulfillment_server.py`(6 工具)、`mcp_risk_server.py`(9 工具),基于 FastMCP |
| Tool 是什么 | `fulfillment_tools.py`(6 个)、`risk_tools.py`(12 个)纯函数;MCP 层只是薄封装 |
| 大模型如何决定调用 Tool | **当前主链路没有 LLM 工具调用**:履约由 Saga 直接驱动工具函数;风控由 Service 直接调用。代码注释明确"内部履约主链路不经过 LLM" |
| 实际 Tool 调用由谁执行 | **平台/代码层**(Saga 步骤、Service),不是 LLM |
| Tool 参数如何生成 | 由上层业务代码构造(SagaContext / kwargs) |
| Tool 参数如何校验 | 结构层用 Pydantic schema;业务层有状态码校验(如 reservation 无效返回 `invalid_reservation`、`kg_store` 对不支持的 relation `raise ValueError`) |
| Tool 执行结果如何返回 | 统一结构化 dict + 状态码(status: reserved/insufficient/locked/persist_failed/not_found...) |
| Tool 结果如何校验 | 调用方按 status 字段分支处理(Saga 步骤校验 `status != "reserved"` 判定失败) |
| 异常如何处理 | 调用方四层防护捕获;业务失败不触发熔断,仅异常触发 |
| 如何避免错误工具调用 | 主链路无 LLM 选工具,天然规避;若未来启用 LLM 调用,需按第四章 4.2 评测标准补齐 |
| MCP 相比传统 Function Calling 的优势 | 协议标准化、跨语言/跨系统复用、传输层解耦、工具集中管理;本项目实际只用到"工具暴露层"这一半能力 |

## 7.2 面试表述模板(避免把"执行"说成"LLM 干的")

> 正确的说法:"**LLM 负责决策/生成调用参数,平台负责实际执行 Tool**。本项目主链路为了保证强一致,履约/风控工具由确定性 Saga/Service 直接驱动,不经 LLM 工具调用;同时我们基于 MCP 协议(FastMCP)把同一批工具封装为标准 MCP Server(stdio/HTTP),供外部 MCP 客户端以标准协议复用,工具输出全部结构化并带状态码,参数经 Pydantic 与业务双重校验。"

> ⚠️ 切忌说"我的系统里 LLM 自主调用 MCP 工具完成了下单"——代码中不存在这条链路。

# 十、核心技术难点(3~5 个,建议重点准备)

> 每个难点按"问题/为什么难/方案/原理/实现/效果/替代方案"组织。以下难点的"优化效果"一律标为【设计目标】,不要填实测数字。

## 难点 1:LLM 重排的稳定性 —— 输出不可靠如何兜底
- **问题**:LLM 语义重排输出可能是非 JSON、包含不存在的商品 ID、或乱序。
- **为什么难**:LLM 生成天然不保证格式与集合约束;重排结果直接决定最终推荐质量。
- **原始方案 / 问题**:早期若直接信任 LLM 输出,可能返回空列表或非法 ID,推荐直接降级失败。
- **方案**:两级兜底——(1) 确定性 `_score_candidates` 先排序;(2) 仅 top-2N 交 LLM,解析失败/无有效 ID 时回退确定性排序;最终结果再与候选集合做 ID 映射过滤,不足补齐。
- **原理**:把 LLM 当作"可失败的优化器",确定性排序为安全基线;输入裁剪控制 token 成本。
- **效果**【设计目标】:LLM 任意失败场景下推荐仍返回合法结果;候选校验率可测(见 `evaluation.py::evaluate_rerank_output`)。
- **替代方案**:结构化输出(Function Calling/JSON Mode)、Prompt 约束+重试、小模型路由、rule-based 全覆盖。

## 难点 2:履约分布式一致性 —— Saga 编排与补偿
- **问题**:库存预占、物流匹配、订单创建跨 Redis/PostgreSQL,中途失败会导致库存泄漏或脏订单。
- **为什么难**:各步骤不在同一事务;预占是 TTL 资源;补偿可能失败。
- **方案**:Orchestration-based Saga 4 步,execute/compensate 各自独立熔断器;失败逆序补偿;补偿失败记 COMPENSATE_FAILED 不阻断;`saga_audit` 全量留痕。
- **原理**:最终一致性;每步可逆(预占→释放、订单→取消);业务失败(库存不足)不触发熔断,仅基础设施异常触发——区分业务语义与故障语义。
- **效果**【设计目标】:正常态成功率 ≥99%、单点故障注入 ≥95%、补偿成功率 ≥95%(均为建议验收线,见指标审查文档 4.5)。
- **替代方案**:本地消息表+MQ、TCC、2PC(强一致但阻塞)、事务性 Outbox。

## 难点 3:AI 写操作的安全边界 —— 门控 + 安全网关
- **问题**:LLM/Meta 决策一旦放行,可能直接触发下单/占库存这类不可逆写操作。
- **为什么难**:写操作不可轻易回滚;需要"AI 建议 + 人工兜底 + 权限控制"三层保险。
- **方案**:
  - 中间件层:限流(fail-closed)→ JWT 鉴权 → PII 双向脱敏 → Prompt 注入检测;履约请求校验 `write` scope,无权限 403;
  - 编排层:`fulfillment_precheck` 先跑反欺诈+授信,再交 Meta 仲裁,`approve` 才走真实 Saga,否则只生成待人工预订单(**不落单、不占库存**);
  - 启动层:开启鉴权但 JWT 密钥缺失 → fail-fast 拒绝启动。
- **原理**:纵深防御;把"决策"与"执行"分离,写操作永远由确定性代码执行且需门控通过。
- **效果**【设计目标】:高风险/低置信度单 100% 拦截或转人工;介入率 ≤5%、人工复核一致率 ≥90%(建议目标)。
- **替代方案**:规则引擎强制覆盖 LLM 决策(无论 LLM 说什么,最终由规则终审)。

## 难点 4:跨域风控冲突仲裁 —— 规则与 LLM 的灰度融合
- **问题**:欺诈、信用、退款三个独立结果可能互相矛盾(如欺诈分高但信用分高)。
- **为什么难**:单一规则无法覆盖冲突语义;全量用 LLM 又引入不确定性与成本。
- **方案**:MetaAgent 双路径——确定性快通道(总分 ≥100 reject / <30 approve)+ LLM 仲裁仅触发于灰度/冲突场景(30≤总分<100、跨域极差 ≥60 vs ≤20、特定高风险组合),LLM 失败回退规则(总分≥60→escalate)。
- **原理**:成本-风险平衡;把 LLM 用在"真正需要语义权衡"的窄带上。
- **效果**【设计目标】:仲裁准确率、escalate 精度、漏放率需真实风控标签评估(PoC 阶段为规划)。
- **替代方案**:决策树/评分卡融合、XGBoost 二分类、完全人工审核。

## 难点 5:外部依赖不可用的优雅降级(多存储降级体系)
- **问题**:Neo4j/Milvus/Redis/PostgreSQL/LLM 任一不可用,链路不能整体不可用。
- **为什么难**:5 类外部依赖 + LLM,故障组合爆炸;降级不能引入安全缺口。
- **方案**:每层降级——LLM→规则/空结果(Agent 降级)、Milvus→内存余弦、Redis→进程内存(fail-closed 限流)、Neo4j→mock 特征、DB→硬编码主数据;熔断器滑动窗口(错误率 ≥50% → OPEN → 30s 后半开探测)。
- **原理**:降级矩阵 + 四层防护统一封装(BaseAgent / BaseProtectedService),业务失败与基础设施故障分离。
- **效果**【设计目标】:单点故障注入下链路成功率 ≥95%。
- **替代方案**:多活部署、旁路缓存预热、异步重试队列。

> 面试官追问优先级建议:难点 2(Saga)> 难点 3(门控安全)> 难点 1(重排兜底)> 难点 4(仲裁)> 难点 5(降级)。
