## 0. 三十秒电梯陈述（建议背下来）

> 这是一个**大型金融电商项目的智能体编排子系统**，我独立负责实现。核心思路不是"用 LLM 替换后端"，而是 **LLM + 确定性的混合架构**：推荐链路的语义重排和营销文案交给 LLM 智能体，风控、授信、退款、履约这些强一致路径用确定性规则和 Saga 事务来保证，跨域冲突由一个 Meta-Agent 在灰度区间做条件性仲裁。用 LangGraph 做双图编排 —— 推荐是三阶段并行图，全局是意图路由的 5 分支动态引擎。工程上做了四层防护（重试/超时/降级/熔断）、Saga 补偿、安全网关和链路追踪。目前是 PoC 阶段，Redis/Milvus/Neo4j/PostgreSQL 都是真实运行的容器，业务数据用的是内置 demo 数据集。

## 1. 项目背景（为什么做）

### 1.1 业务背景

电商平台的推荐、风控、履约、售后长期是**四套各自独立的系统**，彼此不感知，产生三个典型问题：

| 问题 | 具体表现 | 本项目做法 |
|---|---|---|
| 推荐与库存/风控脱节 | 推荐了缺货商品；给高风险用户推高价商品 | 推荐结果必须过库存过滤；高风险时由 Meta-Agent 跨域仲裁 |
| 各系统决策互相冲突 | 反欺诈判高危、信用评估却通过，谁来拍板 | Meta-Agent 汇总各域风险分，规则快通道 + LLM 灰度仲裁 |
| 履约写操作无门控 | 风控没过就已经下单占库存 | 履约前预检（反欺诈+授信）→ Meta 批准才真实下单，否则转人工预订单 |

### 1.2 技术动机（这是面试官真正想听的）

不是"为了用 Agent 而用 Agent"，而是一条清晰的职责边界：

- **LLM 擅长什么** → 语义理解、创意生成、模糊地带的权衡判断 → 商品语义重排、营销文案、跨域灰度仲裁
- **LLM 不擅长什么** → 确定性计算、强一致事务、可复现的风控决策 → 规则引擎、评分卡、Saga 事务

> **一句话结论**：LLM 做"判断力"，确定性代码做"可靠性"。把 LLM 放在它真正增值的位置，而不是让它去承担事务一致性。

### 1.3 为什么不直接全用 LLM

三个硬约束（面试加分点）：
1. **风控不可复现** → 监管要求决策可追溯、可解释，LLM 输出不确定，必须用规则引擎 + 评分卡
2. **事务一致性** → 下单占库存是分布式事务，需要 Saga + 补偿，LLM 无法保证
3. **成本与延迟** → 全链路 LLM 调用成本高、延迟不可控，只在重排/文案/灰度仲裁三处调用

## 2. 用户角色（谁在用）

**这是一个 B 端（系统间调用）服务，不是 C 端消费者产品。** 这点必须先说清楚，否则容易被追问穿帮。

| 角色 | 使用方式 | 对应接口 |
|---|---|---|
| **上游业务系统**（App/小程序服务端） | 通过 HTTP 调用统一入口 `/api/v2/process`，由 `intent` 字段分发 | 推荐、反欺诈、授信、退款、履约 5 类场景 |
| **风控/信审运营人员** | 处理系统 `escalate` 转人工的单据 | `/api/v2/fraud/check`、`/credit/assess`、`/refund/assess` 返回的 `needs_human_review` 字段 |
| **算法/研发人员** | 查看实验状态、链路追踪、监控指标、工作流状态 | `/api/v1/experiments`、`/api/v2/traces`、`/api/v1/metrics`、`/api/v2/workflows` |
| **运维/安全** | 健康检查、LLM 路由状态、护栏开关 | `/health`、`/api/v1/llm/status` |

**关键设计**：所有 API 请求先过安全网关中间件（限流 → 鉴权 → PII 脱敏 → Prompt 注入检测），履约等写操作额外校验 `write` scope，无权限直接 403。

## 4. 系统链路（怎么跑）

### 4.1 全局链路：动态引擎（5 分支意图路由）

```
请求 → 安全网关（限流→鉴权→PII脱敏→注入检测）
     ↓
  intent_router（意图识别：规则优先，LLM 兜底）
     ↓ 条件边分发
  ┌──────────────┬──────────────┬──────────────┬──────────────┬──────────────────┐
  │ recommendation│ fraud_check  │credit_assess │refund_review │ fulfillment_precheck│
  │  推荐链路     │  反欺诈规则  │  信用评分卡  │  退款风控    │  反欺诈+授信      │
  └──────────────┴──────────────┴──────────────┴──────────────┴─────────┬────────┘
     ↓                                                                   ↓ Meta 仲裁
  meta_agent（跨域决策）                                    条件边：approve → 真实下单
     ↓                                                              reject/escalate → 待人工
   END
```

- **意图路由**：`INTENT_KEYWORDS` 关键词规则优先（可控、零延迟），匹配不上时可选 LLM 兜底（默认关闭，`intent_router_use_llm=False`）
- **履约门控**（重要设计）：`approve` 才走 `fulfillment_execute` 真实创建订单占库存；`reject`/`escalate` 走 `fulfillment_pending`，**只生成待人工确认预订单，不落单、不占库存**

### 4.2 推荐主链路：三阶段 LangGraph 并行图

```
      init（请求ID / A-B分桶）
       │
   ┌───┴───┐  fan-out 并行
   ▼       ▼
user_profile  product_recall        Stage 1：画像 ∥ 召回
   │       │
   └───┬───┘  fan-in 汇合
   ┌───┴───┐  fan-out 并行
   ▼       ▼
 rerank   inventory                 Stage 2：LLM重排 ∥ 库存校验
   │       │
   └───┬───┘  fan-in 汇合
       ▼
    filter（重排结果 ∩ 可用库存）
       ▼
 marketing_copy（LLM 个性化文案 + 广告法合规）
       ▼
   aggregate → END
```

**关键实现细节**（面试加分）：
- 用 LangGraph **原生 fan-out / fan-in 边**实现并行，而不是 `asyncio.gather` 包单节点 —— 并行语义由图结构保证，可视化和可观测性更好
- 并行分支写同一 `agent_results` 字段，用**自定义 channel reducer** (`_merge_agent_results`) 合并，各分支写不同子 key 不冲突
- **不是 `asyncio.gather` 一把梭**，Stage 2 必须等 Stage 1 全部完成（图结构天然 join）

### 4.3 多路召回

| 通道 | 实现 | 降级策略 |
|---|---|---|
| 向量召回 | Milvus + BGE-small-zh，商品文本化 = name+category+brand+tags+description[:100] | Milvus 挂了 → 内存余弦；embedding 挂了 → signed hashing trick |
| 协同过滤 | UserCF，Jaccard 相似度，权重 purchase=3/favorite=2/view=1 | 服务不可用 → 返回空，不阻塞主链路 |
| 图谱召回 | Neo4j 多跳 + 共购关系挖掘 | 不可用 → 返回空列表 |
| 热度兜底 | 全量商品池 | 保证永远有结果 |

### 4.4 三层 LLM 混合架构（核心卖点）

| 层 | LLM 介入方式 | 代码位置 |
|---|---|---|
| **推荐链路** | 语义重排 + 营销文案，**无条件介入** | `ProductRecAgent` / `MarketingCopyAgent` |
| **跨域仲裁** | Meta-Agent 在风险分灰度区间 [30,100) **条件性触发** LLM | `agents/meta_agent.py` |
| **强一致路径** | **纯确定性**，风控/授信/退款/履约 Saga 不经过 LLM | `services/*.py` |

**Meta-Agent 双路径决策**（这是设计亮点）：
```
风险总分 ≥100        → 规则快通道直接 reject     （<1ms，不调 LLM）
风险总分 <30         → 规则快通道直接 approve    （<1ms，不调 LLM）
30 ≤ 风险 < 100      → LLM 仲裁灰度通道          （条件触发）
跨域信号冲突          → LLM 仲裁                 （max≥60 且 min≤20）
LLM 不可用            → 降级回规则引擎，主链路不中断
```
决策结果带 `arbitration_source` 字段（`rule_fast_reject` / `llm_arbitration` / `rule_fallback`），**决策来源可追溯** —— 这是风控场景的刚需。

## 5. 技术选型（为什么这么选）

| 选型 | 选择 | 为什么（要能说出取舍） |
|---|---|---|
| **编排框架** | LangGraph | 需要**有状态、可并行、可持久化**的图编排。原生 fan-out/fan-in + channel reducer 正好匹配推荐的并行拓扑；相比纯 `asyncio.gather`，图结构是声明式的，可读性和可观测性更好 |
| **API 框架** | FastAPI | 原生 async、Pydantic 模型校验开箱即用（全链路 schema 强类型），自动 OpenAPI 文档；中间件机制便于插入安全网关 |
| **LLM 编排层** | LangChain + langchain-openai | 统一 OpenAI 兼容接口，**云 API 和本地 vLLM 切换只需改 base_url**，这是能同时支持 DeepSeek 云上和 vLLM 本地的前提 |
| **模型路由** | 自建 `MultiModelRouter`（flash/general/reasoning 三档） | 不同任务对能力要求差异大：意图识别用 flash 省钱，创意任务用 general，**风控/决策用 reasoning（DeepSeek-R1）**。按任务路由 + 健康检查降级 |
| **推理部署** | DeepSeek 云 API + vLLM（可选 GPU profile） | vLLM 用 OpenAI 兼容协议，本地化只需改环境变量；docker-compose 里设为 `profiles: ["gpu"]`，无 GPU 环境也能一键 up |
| **向量库** | Milvus | 生产级 ANN，支持 HNSW 索引 + 标量字段过滤；相比 FAISS 有独立服务、持久化、分布式能力 |
| **图数据库** | Neo4j | 知识图谱需要**多跳关系查询**（共购、同品类、偏好传播），关系型数据库的递归查询表达力不够 |
| **Embedding** | BAAI/bge-small-zh-v1.5 | 中文语义检索效果好的小模型，512 维，本地可跑，不需要 GPU |
| **缓存/特征** | Redis | 限流滑动窗口、库存预占锁（SETNX）、CF 索引、行为特征，TTL 自然过期 |
| **事务** | 自研 Saga（编排式） | 履约跨库存/物流/订单三个服务，无分布式事务中间件；Saga + 逆序补偿是最务实的方案 |
| **工具协议** | MCP（FastMCP） | 把履约/风控工具封装成标准 MCP 工具，供外部客户端调用（stdio / HTTP 双传输） |
| **可观测** | 自建 Tracing（类 LangSmith 风格） | 需要按 request_id 追踪 Agent 调用链；生产可对接 LangSmith/Phoenix |

### 5.1 一个重要的诚实说明

> **MCP 在项目里是「工具暴露层」，主链路不经过 LLM 工具调用。** 内部履约链路由 Saga 直接调用 `fulfillment_tools.py`，不走 MCP、不经过 LLM —— 这是刻意的，因为事务路径不能依赖模型输出。MCP Server 是给外部系统（运维工具、第三方集成）用的标准接口。
>
> 面试时**不要**把 MCP 包装成"Agent 通过 MCP 自主调用工具完成下单"，那是没实现的，一问就穿。

### 6.1 按模块归因（8 项，均有代码依据）

**① LLM 智能体实现（3 个）**
- `ProductRecAgent`：多路召回融合 → 确定性预打分 → LLM 语义重排（top-N×2 截断）→ 失败回退到确定性打分
- `MarketingCopyAgent`：用户分群模板选择 → LLM 生成 → 广告法禁用词过滤
- `MetaAgent`：规则快通道 + LLM 灰度仲裁 + 规则降级三层决策

**② 多模型路由**
- `llm/router.py`：flash / general / reasoning 三档按任务类型路由，模型不健康时自动降级到 general；vLLM 模式下自动关闭路由（只有一个本地模型）

**③ 知识图谱搭建**
- `services/kg_store.py`：5 类节点（User/Product/Category/Brand/Seller）、7 类关系（VIEWED/PURCHASED/FAVORITED/BELONGS_TO/BRANDED_BY/SOLD_BY/RELATED_TO），MERGE 幂等写入，Jaccard / 度中心性 / 多跳查询原语
- 共购关系挖掘：`build_co_purchase_relations()` 用 Cypher 从 PURCHASED 边计算（support≥2，weight=1-1/(support+1)）
- `services/graph_rag.py`：子图证据 → 结构化 LLM 上下文注入

**④ LangGraph 双图编排**
- `orchestrator/graph.py`：推荐三阶段 fan-out/fan-in 图 + 自定义 channel reducer
- `orchestrator/dynamic_engine.py`：意图路由 + 5 分支条件边 + 履约预检门控

**⑤ 可靠性工程（四层防护）**
- `agents/base_agent.py` / `services/base_service.py`：重试（tenacity 指数退避 500ms→1s→2s）+ 独立超时（`asyncio.wait_for`，每次尝试独立计时）+ 确定性降级 + 熔断（滑动窗口错误率，CLOSED/OPEN/HALF_OPEN 三态）

**⑥ Saga 分布式事务**
- `services/saga.py`：4 步（查库存 → 预占 → 物流匹配 → 建单），逆序补偿，**execute 和 compensate 各自独立熔断器**（补偿失败不阻断后续补偿）

**⑦ 安全网关**
- `services/guardrails.py` + `main.py` 中间件：Prompt 注入防护（9 条正则 + base64 间接注入检测）、PII 入站/出站双向脱敏、JWT 鉴权、Redis 滑动窗口限流（Redis 挂了降级到本地令牌桶，**fail-closed** 而非放行）

**⑧ 可观测与实验**
- `services/tracing.py`：Span/Trace 两级追踪，记录输入/输出/耗时/Token/错误
- `services/ab_test.py`：Thompson Sampling + 一致性哈希分桶
- `services/workflow_engine.py`：Temporal 风格持久化工作流骨架
- `services/evaluation.py`：Precision@K / NDCG@K / 多样性 / 覆盖率

### 6.2 问题 → 方案 → 成果（推荐用这个叙事，比罗列技术点更有说服力）

| 问题 | 方案 | 成果 |
|---|---|---|
| LLM 与事务一致性不可兼得 | 三层混合架构，推荐链 LLM 无条件、跨域灰度条件、强一致路径确定性 | 风控/履约零 LLM 依赖，决策可追溯 |
| 并行链路编排刚性 | LangGraph 原生 fan-out/fan-in + channel reducer | 推荐链路 3 阶段，Stage 间天然 join |
| 跨域风险冲突无人拍板 | Meta-Agent 双路径决策 | 决策来源可追溯（`arbitration_source` 字段） |
| 履约写操作未门控（P1） | 预检 → Meta 仲裁 → 条件边 | approve 才落单占库存，reject 转人工预订单 |
| 安全基线缺失（P0/P1） | 四合一安全网关 | 鉴权默认 fail-fast、限流 fail-closed、出站 PII 脱敏 |
| 依赖故障级联雪崩 | 四层防护 + 熔断 | LLM 不可用自动降级，主链路不中断 |
| 单模型成本与延迟 | 三档模型按任务路由 | 意图识别等简单任务用小模型 |
| 召回结果不可复现 | 排序 tie-breaker 从 `random.random()` 改为 `hashlib.md5` 确定性哈希 | 修复 flaky 测试，结果稳定可复现 |

## 7. 难点问题（遇到了什么坑）

### 7.1 LLM 输出不确定性 vs 风控可复现性（架构级难点）

**问题**：风控决策必须可解释、可复现，但 LLM 输出不确定。
**解决**：划定灰度区间 —— 风险分 <30 和 ≥100 走规则快通道（<1ms，零 LLM 调用），只有中间的 [30,100) 灰度区间和跨域信号冲突才触发 LLM 仲裁，且 LLM 失败自动降级回规则。
**关键**：每条决策记录 `arbitration_source`，出问题时能追溯是"规则拒的"还是"LLM 拒的"。

### 7.2 并行分支的状态合并冲突

**问题**：LangGraph 并行分支同时返回 `agent_results`，后写的覆盖先写的。
**解决**：自定义 channel reducer `_merge_agent_results()` 做浅合并，各分支约定只写自己的子 key。
**踩坑点**：一开始想用 `Annotated[dict, operator.add]`，但 dict 相加会报错，必须自己写 reducer。

### 7.3 Saga 补偿本身也会失败

**问题**：补偿动作（释放库存、取消订单）自己也可能失败，失败后整个补偿链断裂。
**解决**：**execute 和 compensate 各自持有独立熔断器** —— 补偿失败时记录 `COMPENSATE_FAILED` 状态并继续后续补偿，不阻断、不抛异常，失败单据进 `saga_audit` 待人工处理。

### 7.4 限流组件故障时的两难

**问题**：Redis 挂了，限流该放行（可用性）还是拒绝（安全性）？
**解决**：选择 **fail-closed** —— Redis 不可用时降级到进程内本地滑动窗口令牌桶，达到容量即拒绝。宁可误杀也不裸奔。

### 7.5 召回结果不可复现（flaky 测试）

**问题**：`_recall` 排序的 tie-breaker 用了 `random.random()`，分数/库存相同时结果随机，导致测试时通过时不通过。
**解决**：改为基于 `product_id` 的 `hashlib.md5` 确定性哈希打散 —— 既保留了打散效果，又保证同输入必得同输出。
**意义**：推荐系统的可复现性是刚需，线上问题要能复现才能排查。

### 7.6 鉴权默认值的隐患

**问题**：原来 `guardrails_jwt_enabled=False` 默认关闭，且 `jwt_secret` 有硬编码默认值 —— 等于生产环境裸奔。
**解决**：改为**默认开启 + 环境变量注入 + 启动强校验（fail-fast）**：密钥缺失或 <32 字符拒绝启动；生产环境（debug=False）检测到 `dev-` 前缀占位密钥也拒绝启动。消除"未配置就静默使用公开密钥"的隐患。

### 7.7 冷启动与上下文覆盖

**问题**：新用户无行为数据，画像为空导致向量召回无 query text。
**解决**：分三层 —— ① `_overlay_context()` 用请求体 `context` 做冷启动覆盖；② 画像空时向量召回返回空，靠热度兜底保证有结果；③ 响应体 `feature_source` 字段如实返回 `"neo4j"` 或 `"mock+context"`，便于排查。

## 8. 优化结果（指标怎么变）⚠️ 最重要的一节

### 8.1 先说结论：这个项目**没有**可引用的业务量化指标

不要写"转化率提升 X%""延迟降低 Y%"。原因：

1. **PoC 无真实流量** —— 没有真实用户请求，无法统计转化率、GMV、CTR
2. **业务数据是 demo 集** —— 15 条商品、5 个用户，统计样本量不足以支撑任何百分比
3. **之前文档中的 8 个量化数字已自查为编造** —— 例如「履约 180s→秒级」「工具调用 81.5%→98.2%」「分期转化率 3.2%→6.9%」「人工介入率 35%→4.2%」「Saga 成功率 82%→99.6%」，其中 4 个逻辑本身就不成立（人工审核不可能秒级；HITL 是新引入的没有基线；无流量无支付链路不可能有转化率）

> **面试官追问"提升了多少"时，正面回答：**
> "这个子系统目前是 PoC，没有真实流量，所以我不会给转化率这类业务数字 —— 给了也是编的。我能给的是工程质量数据和架构能力，以及如果要上量应该怎么衡量。"

### 8.2 ✅ 可以写的（有实测依据）

| 指标 | 数值 | 依据 |
|---|---|---|
| **测试通过** | 147 个用例全部通过 | pytest 全量收集 147 例，修复 flaky 后全绿 |
| **确定性链路延迟** | 风控 0.5ms / 信用评估 0.3ms / 退款风控 0.2ms / 履约 Saga(4步) 0.9ms / Meta 规则快通道 <0.1ms | `tests/test_benchmark.py` 实测输出（`time.perf_counter`） |
| **安全修复** | 4 项 P0/P1 安全问题修复落地并补测试 | 鉴权 fail-fast、履约门控、出站 PII 脱敏、限流 fail-closed |
| **flaky 修复** | 召回排序从 `random.random()` 改为确定性哈希，测试从「时过时不」到稳定通过 | `agents/product_rec_agent.py` |
| **架构能力** | Saga 逆序补偿 + 双熔断器、四层防护、决策来源可追溯、LLM 降级不中断 | 代码可演示 |

### 8.3 ⚠️ 弱证据（可用但要说明口径）

| 指标 | 数值 | 必须说明的口径 |
|---|---|---|
| Precision@5 | 0.68 | 样本仅 5 个用户（`GROUND_TRUTH`），且走的是**确定性打分降级路径**，不是 LLM 精排 |
| 类目多样性 | 0.72 | 同上 |
| 目录覆盖率 | 0.93 | 目录仅 15 个 SKU |
| NDCG@5 | 1.00 | **不可用** —— 每个类目只有 1-3 个 SKU，IDCG 分母极小，满分是假象 |

**如果使用这些数字，必须补一句**："这是 15 个 SKU 的 demo 数据集上的离线评测，样本量太小，只用于验证评测管线跑通，不代表真实效果。"

### 8.4 如果要上量，应该衡量什么（展示思考深度）

| 类别 | 指标 | 口径/公式 |
|---|---|---|
| 推荐效果 | CTR、CVR、NDCG@K | 需 ≥1000 用户真实行为样本，离线 replay + 在线 A/B 双验 |
| 风控效果 | 精确率、召回率、人工介入率 | 需标注数据集；介入率目标 ≤5%，精度 ≥90% |
| 履约可靠性 | Saga 成功率、补偿成功率、p95 耗时 | 故障注入 ≥500 次，补偿成功率 ≥95% |
| 工程 | p95/p99 延迟、LLM 降级触发率、Token 成本 | 需接 Prometheus + 持久化 |

> **加分说法**："A/B 框架（Thompson Sampling）和评测模块（Precision/NDCG/多样性/覆盖率）我都实现好了， Thompson 采样目前是死代码 —— 因为没有人上报结果后验，采样不会收敛。等有真实流量接进来，这套东西直接就能用。"
